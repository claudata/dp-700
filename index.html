Domain 1 · 30–35%

Implement and manage an analytics solution

Implementar e gerenciar uma solução analítica.

Você precisa reconhecer como organizar os workspaces, promover mudanças entre ambientes, proteger os dados e coordenar tarefas de processamento.

1.1 Configurações de workspace

Um workspace é uma fronteira de colaboração e administração para itens Fabric. As configurações disponíveis podem controlar comportamento de Spark, associação a domínio, uso do OneLake e recursos do Apache Airflow. O princípio de projeto é definir configurações de acordo com o padrão operacional do workspace, documentá-las e verificar impacto em custos, segurança e colaboração antes de mudar.

  • Spark workspace settings: estude as configurações de Spark disponíveis no workspace e consulte a documentação oficial para as opções e limites atuais.
  • Domain workspace settings: estude como o workspace é configurado em relação a um domain; domain não substitui permissões de acesso.
  • OneLake: avalie as opções de governança, acesso e organização de dados em escala do workspace/tenant.
  • Apache Airflow workspace settings: revise as configurações incluídas no Study Guide e consulte a documentação do recurso para configuração e uso.

1.2 Ciclo de vida e implantação

Lifecycle management (ALM) é o conjunto de práticas que permite desenvolver, revisar, testar e promover alterações com rastreabilidade. Versionamento registra mudanças; projetos de banco de dados ajudam a tratar artefatos de banco como código; deployment pipelines promovem conteúdo entre estágios. Defina como lidar com parâmetros e diferenças de ambiente, quem aprova promoções e como reverter uma alteração problemática.

Modelo mental: desenvolver → revisar/versionar → testar → promover → verificar. A promoção não elimina a necessidade de validar permissões, conexões e configurações do ambiente de destino.

1.3 Security and governance

Separe as perguntas “quem pode acessar o workspace ou item?” de “quais dados essa pessoa pode ver?”. Combine controles de acesso apropriados com proteção no nível dos dados. Aplique o princípio de menor privilégio e teste com identidades representativas dos usuários.

Camada / recursoO que ajuda a controlarPergunta de revisão

Identificar o execution context de um notebook

Objetivo: localizar notebook, workspace e default Lakehouse antes de configurar orchestration. Este script consulta o contexto; não configura ALM ou security.

1 · Preparar o notebook

Abra um Fabric notebook em Python (PySpark) no workspace de treinamento. Se quiser examinar o default Lakehouse, anexe-o ao notebook. Não é necessário criar tabela para este script.

2 · Executar o script

Copie o código abaixo para uma célula e selecione Run cell. O pacote NotebookUtils está disponível no runtime Fabric; não instale um pacote homônimo com pip.

3 · Verificar a saída real

Confira Notebook, Workspace e Lakehouse. Sem default Lakehouse, o exemplo imprime None. Nomes e valores dependem do ambiente; não publique metadados do seu tenant sem revisão.

4 · Debrief com o grupo

Peça ao participante para apontar o workspace correto antes de executar uma atividade. Depois compare execução interativa com execução por pipeline no Lab 1. Contexto não substitui verificação de permissões.

Script · Python (PySpark) · somente leitura 
context = notebookutils.runtime.context

print(f"Notebook: {context['currentNotebookName']}")
print(f"Workspace: {context['currentWorkspaceName']}")
print(f"Lakehouse: {context['defaultLakehouseName'] or 'None'}")

Domain 2 · 30–35%

Ingest and transform data

Ingerir e transformar dados.

A prova cobre decisões de carga, seleção de armazenamento e engine, transformação em lote e processamento de eventos contínuos.

2.1 Full load e incremental load

Full load carrega o conjunto de dados completo. Incremental load carrega dados novos ou alterados de acordo com o padrão de mudança disponível na origem. Escolha o padrão conforme a origem e os requisitos da solução; considere como o processo trata atualizações, exclusões, falhas e reprocessamento.

  • Identifique como a origem indica registros novos ou alterados e quais limitações existem.
  • Defina como a execução trata falhas e reprocessamento, sem assumir uma estratégia única para todas as fontes.
  • Inclua updates, deletes, duplicatas e late-arriving data na análise do padrão de carga.

2.2 Armazenamento e ferramentas de lote

Escolha onde persistir os dados e como transformá-los conforme formato, consulta, interoperabilidade, latência e padrões de consumo. No Fabric, alternativas incluem Lakehouse, Warehouse, Eventhouse e outros itens de dados. Em batch, pipeline pode fazer ingestão e coordenar passos; Dataflow Gen2, notebook, KQL ou T-SQL podem transformar, dependendo do caso.

RecursoIdeia centralQuestão para decidir
LakehouseDados em OneLake com arquivos/tabelas, adequado a workloads lake e Spark/SQL.Precisa de flexibilidade de arquivos, engenharia Spark e tabelas analíticas?
WarehouseExperiência centrada em SQL para dados relacionais e análises.O caso se encaixa em consultas SQL e modelagem relacional gerenciada?
EventhouseArmazenamento/consulta orientados a eventos e dados de série temporal com KQL.Há necessidade de exploração e análise operacional de eventos?
Shortcut / mirroringAlternativas para acessar dados sem necessariamente montar a mesma cópia tradicional.Precisa de acesso referenciado ou replicação gerenciada, e quais são as implicações?

Shortcuts do OneLake referenciam dados em outro local suportado e evitam duplicação de cópia lógica em certos cenários; dependem da disponibilidade da origem e de permissões corretas. Mirroring replica dados de fontes suportadas para o Fabric para cenários analíticos próximos do tempo real. Compare origem suportada, latência, custos, atualização, governança e requisitos de transformação antes de escolher.

2.3 Data preparation and transformation

Dimensionalizar é organizar dados para análise em torno de fatos (eventos/medidas) e dimensões (contexto descritivo). A preparação pode incluir chaves substitutas, padronização, deduplicação, agregação e denormalização para consumo. Preserve significado de negócio e rastreabilidade, e defina comportamento para problemas de qualidade.

  • Duplicatas: defina chave natural/evento, regra de sobrevivência e idempotência.
  • Valores ausentes: distinga “desconhecido”, “não aplicável” e erro de origem; não substitua por zero sem justificativa.
  • Atrasos: escolha se eventos tardios atualizam agregados, entram em correções ou são encaminhados para tratamento.
  • Agregação: preserve granularidade e evite somar medidas não aditivas de maneira incorreta.

2.4 Streaming data, Eventstream e windowing functions

Streaming trata eventos continuamente e exige decidir latência, ordenação, estado, janelas, duplicação, tolerância a atraso e destino. O guia lista Eventstream, Spark Structured Streaming e KQL como competências de processamento. Eventstream ajuda a configurar fluxo de eventos e roteamento; Spark pode implementar transformações stateful/código; KQL é central em exploração e processamento no Real-Time Intelligence.

O Study Guide inclui windowing functions como objetivo. O tipo de janela e os detalhes de configuração dependem do mecanismo escolhido; consulte a documentação oficial de Eventstream, Spark Structured Streaming ou KQL para a implementação específica. O exercício desta página usa um cenário de janela para praticar a leitura do requisito, não prescreve sintaxe.

Tabelas nativas x shortcuts em Real-Time Intelligence: compare necessidade de ingestão/armazenamento local e performance previsível com acesso referenciado ao dado. O guia diferencia shortcuts padrão de opções com query acceleration; avalie a origem, o perfil de consulta, atualização e a configuração atualmente suportada.

  • Preparar dados para modelo dimensional
  • Projetar carga de streaming

  • Selecionar Dataflows Gen2, notebooks, KQL ou T-SQL
  • Criar e administrar OneLake shortcuts
  • Implementar mirroring
  • Ingerir via pipelines

Ler CSV com schema e executar grouping/aggregation

Pré-requisitos: complete a preparação de orders.zip e default Lakehouse. O arquivo 2019.csv do laboratório não tem header; por isso o exemplo aplica um schema explícito.

1 · Conferir origem

No Lakehouse Explorer, confirme Files/orders/2019.csv. Abra o notebook a partir desse Lakehouse e confirme o default Lakehouse com o script do Domain 1.

2 · Ler com schema

Execute o script abaixo no notebook. Compare os nove campos do schema com o arquivo oficial; a célula display(df) deve mostrar colunas nomeadas, não _c0, _c1.

3 · Examinar aggregation

Na segunda saída, verifique uma linha por Item e a soma de Quantity. No exemplo oficial, Quantity é a única coluna numérica restante após select; o resultado não é Revenue.

4 · Variar usando a fonte

O laboratório oficial também mostra a leitura de Files/orders/*.csv para 2019–2021. Faça essa extensão seguindo a fonte e confira os anos. Não trate essa leitura completa como uma implementação de incremental load.

Script · Python (PySpark) · leitura e aggregation 
from pyspark.sql.types import *

orderSchema = StructType([
    StructField("SalesOrderNumber", StringType()),
    StructField("SalesOrderLineNumber", IntegerType()),
    StructField("OrderDate", DateType()),
    StructField("CustomerName", StringType()),
    StructField("Email", StringType()),
    StructField("Item", StringType()),
    StructField("Quantity", IntegerType()),
    StructField("UnitPrice", FloatType()),
    StructField("Tax", FloatType())
])

df = spark.read.format("csv").schema(orderSchema).load("Files/orders/2019.csv")
display(df)

productSales = df.select("Item", "Quantity").groupBy("Item").sum()
display(productSales)

Domain 3 · 30–35%

Monitor and optimize an analytics solution

Monitorar e otimizar uma solução analítica.

Operação envolve perceber um problema, seguir a linhagem das dependências, identificar a causa e confirmar que a correção melhorou o resultado.

3.1 Monitor Fabric items

O Study Guide pede monitoramento de data ingestion, data transformation e semantic model refresh, além de alert configuration. Ao praticar, consulte os recursos de monitoramento disponíveis para cada item e avalie as etapas do cenário; um status concluído em uma atividade não confirma, por si só, a atualização de todas as etapas seguintes.

3.2 Método para identificar erros

  1. Defina o sintoma e o horário: dado ausente, atraso, falha ou degradação.
  2. Localize o item e a execução afetada; leia mensagem, atividade, parâmetros, logs e dependências.
  3. Verifique fonte, credenciais/conexões, permissões, esquema, limites e alterações recentes.
  4. Reproduza com um subconjunto seguro; formule hipótese e mude uma variável por vez.
  5. Corrija, reexecute com segurança e verifique qualidade, etapa downstream e frescor do consumo.
  6. Registre causa, ação corretiva, prevenção e alerta/runbook que reduzirá o tempo para detectar.

O guia inclui erros de pipelines, Dataflow Gen2, notebooks, Eventhouse, Eventstream, T-SQL e OneLake shortcuts. Para shortcuts, por exemplo, investigue disponibilidade da origem, caminho, permissões e alterações na localização; para um erro SQL, verifique objeto, tipo, esquema, consulta e contexto de execução.

3.3 Otimização: medir, encontrar, ajustar

Estabeleça uma linha de base antes de otimizar. Use duração, throughput, volume, uso de recursos, plano de consulta e frescor. Ajuste o componente que domina o custo/latência e repita a medição.

ÁreaInvestiguePrimeiro princípio

PipelineEtapas seriais, cópias repetidas, concorrência e gargalos de origem/destino.Reduza movimentos/etapas e paralelize somente quando seguro.

Domain 3 · Demo guiada

Correlacionar notebook e Monitoring hub

Escopo: logging de contexto e observação de uma execução. Não é benchmark, não configura alertas e não faz otimização automática.

1 · Registrar contexto

Execute o script em um Fabric notebook. Identifique workspace/notebook na mensagem. O currentRunId é específico de reference runs; o fallback “interactive” deste exemplo não é prova de que uma execução não veio de pipeline.

2 · Abrir Monitor

Abra Monitor na navegação Fabric e localize a atividade pelo item, workspace e horário. Siga o laboratório oficial para criar atividades observáveis de notebook e Dataflow Gen2.

3 · Inspecionar evidência

Use Historical runs e View detail, conforme disponível no item. Registre Status, Start time, End time e Duration; só use números obtidos da execução real. A visibilidade depende das suas permissões.

4 · Debrief operacional

Compare as execuções e investigue mudanças em entrada, recursos e etapas antes de atribuir uma diferença a uma otimização. Status Succeeded não comprova qualidade nem semantic model refresh downstream.

Script · Python (PySpark) · contexto para logging 
context = notebookutils.runtime.context

run_id = context.get("currentRunId") or "interactive"
log_prefix = (
    f"[{context['currentWorkspaceName']}/{context['currentNotebookName']}]"
    f" run={run_id}"
)

print(f"{log_prefix} Processing started")

Fontes: exemplo “Include context in logging” de NotebookUtils runtime context e roteiro Monitor Fabric activity in the monitoring hub — MicrosoftLearning.

Aprendizagem prática

Laboratórios guiados

Os cenários abaixo são exercícios didáticos autorais para praticar os tópicos do Study Guide; não são instruções oficiais de configuração nem questões do exame. Use um workspace de treinamento e siga a documentação oficial do item escolhido. Se não tiver acesso ao Fabric, conclua o desenho e as perguntas de revisão sem executar alterações.

Laboratório 1 · Ambientes, acesso e orquestração

Tempo sugerido: 45–60 min · Domínio: implementar e gerenciar

Cenário: uma equipe publica dados de pedidos para analistas. Há desenvolvimento, teste e produção; analistas só podem acessar os dados necessários; a carga noturna inicia após a entrega de arquivos.

Parte A — Desenho (sem workspace)

  1. Desenhe três estágios e identifique quem cria, revisa, aprova e consome em cada um.
  2. Liste os itens (pipeline, notebook ou Dataflow Gen2, Lakehouse/Warehouse) e as conexões por ambiente.

Glossário essencial

OneLake
Camada lógica de armazenamento unificada do Fabric para dados analíticos.
Lakehouse
Item que combina padrões de lake com tabelas e experiências de engenharia/consulta.
Shortcut
Referência a dados em um local suportado, sem uma cópia tradicional gerenciada como ingestão local.
Mirroring
Replicação contínua de fontes suportadas para análise no Fabric, sujeita às capacidades e limitações do conector.
Watermark
Valor de controle que indica até onde uma carga incremental foi processada/confirmada.
Idempotência
Propriedade pela qual repetir uma operação produz o mesmo estado final, sem efeitos duplicados indesejados.
RLS / CLS / OLS
Controles de segurança associados a linhas, colunas e objetos; suporte e configuração variam por item/engine.
Eventstream
Recurso Fabric para receber, transformar/rotear e enviar fluxos de eventos a destinos suportados.
Eventhouse / KQL
Ambiente e linguagem orientados a exploração/consulta analítica de eventos e dados temporais.
Watermark de streaming
Limite temporal usado pela abordagem de processamento para definir tolerância a eventos tardios.
